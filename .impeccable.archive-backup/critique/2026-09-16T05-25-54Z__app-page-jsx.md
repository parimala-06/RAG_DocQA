## Overall Impression

This is a well-crafted, intentionally-designed UI — it doesn't read as templated, and the core "answer with clickable citation" interaction is genuinely good. But three real trust/control gaps keep it from feeling finished: the delete confirmation can silently expire or misfire, users can't tell which documents an answer is even drawing from, and failures surface as raw JS error strings. The single biggest opportunity is closing the query-scope visibility gap — for a tool whose entire pitch is "trace every answer back to its source," not showing what's in scope before you ask undercuts the core promise.

## What's Working

1. **The citation-marker toggle** (`page.jsx:196-206`, styled via `.citation-marker` in `globals.css`) — a real interaction idea that directly serves the "trace every answer back to its source" tagline, not decoration.

## Priority Issues

**[P1] Silent, un-cued delete-confirm timeout**
- Why it matters: Clicking Delete arms a 4-second silent confirm window (`page.jsx:126`) with no visible countdown. A user who pauses gets the confirm silently reverted with no warning; a fast double-click deletes with no true "are you sure" moment. Heuristic 5 (Error Prevention) failure.
- Fix: Show a visible countdown/progress indicator inside the "Confirm?" button itself, or replace the timing-based pattern with an explicit toggle that only reverts on outside click / Escape.
- Suggested command: `/impeccable harden`

**[P1] No question-scope visibility**
- Why it matters: The Q&A pane never states whether an answer draws from all uploaded documents or a subset. For a citation-driven trust tool this is the single most important status the UI is missing — a Heuristic 1 (Visibility of System Status) failure and the one working-memory checklist item that fails outright.
- Fix: Add a small scope indicator above the input (e.g. "Searching 3 documents") or let the user scope a question to specific documents.
- Suggested command: `/impeccable clarify`

**[P1] Raw error strings with no recovery path**
- Why it matters: Fetch failures surface as `Error: ${err.message}` directly in the chat thread (`page.jsx:178`) and bare text in the sidebar (`page.jsx:288`). No distinction between "no documents yet," "server down," or "network blip," and no retry affordance — a Heuristic 9 dead end.
- Fix: Map known error cases to plain-language messages with a retry button; keep raw messages behind a collapsed "details" toggle for the rare unknown case.
- Suggested command: `/impeccable harden`

**[P2] No upload-in-flight cancel or progress**
- Why it matters: Once "Reading and embedding…" starts (`page.jsx:280`) there's no cancel and no percentage — for a large PDF the user has no control and no time estimate.
- Fix: Add a cancel affordance and, if feasible, incremental progress.
- Suggested command: `/impeccable polish`

**[P2] Zero help/onboarding affordance**
- Why it matters: Nothing teaches the citation-click interaction beyond one placeholder line (Heuristic 10 scored 1/4); a first-timer has to discover it unaided, and nothing gates asking a question before any document is uploaded.
- Fix: A one-time dismissible hint near the first citation marker, or a small "?" affordance in the header; gate the ask input (or its copy) when the archive is empty.
- Suggested command: `/impeccable onboard`

## Persona Red Flags

Interface type: task tool for uploading/querying documents → **Alex, Jordan, Sam**.

**Alex (Power User):** No bulk upload — the file input accepts one file at a time (`e.target.files?.[0]`, `page.jsx:91`) — and no bulk delete. Uploading 15 research PDFs means repeating the single-file dropzone interaction 15 times; Alex scripts around it or leaves.

**Jordan (First-Timer):** The preview-PDF eye icon (`page.jsx:342-351`) is icon-only in the visible UI — a11y label exists, but a first-timer scanning visually just sees an unlabeled glyph. Nothing stops Jordan from typing a question before uploading anything, so their very first action can land on a confusing error instead of a helpful gate.

**Sam (Accessibility-Dependent):** Global focus-visible ring is implemented (`globals.css`) — good. But the citation excerpt reveal has no `aria-live` announcement of the revealed content itself (only `aria-expanded` on the button), so a screen-reader user may not hear the excerpt without manually re-navigating to it.

## Minor Observations

- "14 chunks" (`page.jsx:354`) exposes implementation jargon to end users with no explanation of what a "chunk" is.
- The detector-flagged `border-l-2 border-clay` accent on the excerpt card (`page.jsx:469`) is a small, common AI-generated-UI tell — cheap to swap for a treatment more specific to the rest of the palette (e.g. a subtle background tint matching `bone`/`paper` without the colored rule).
- The summary modal's loading state is plain text ("Reading the whole document…") while the sidebar's equivalent pairs text with an icon — a small inconsistency between the two "working" states.
- Sidebar doc row (`page.jsx:307-381`) packs icon + filename + preview link + chunk count + 2 buttons into two dense rows; will feel cramped once a user has more than a handful of documents.
